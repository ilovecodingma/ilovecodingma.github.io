3장. 멀티에이전트 업무 분담의 시작

처음에는 에이전트 하나로 충분해서, 만들고 싶은 것을 말하면 코드를 고쳐 화면을 보여 주고 마음에 들지 않으면 다시 바꿔 주었으며, 서비스 몇 개를 하루 만에 만들었다가 없애는 동안에도 누구에게 맡길지를 고민할 필요 없이 같은 세션에 말하면 됐다. 그런데 사이트가 구체적인 모양을 갖춰 가면서 내가 시키는 일은 계속 느는데 말을 듣는 상대는 여전히 하나라는 것이 문제가 되기 시작했고, 자료를 찾으라고 했다가 화면을 고치라고 하고 수집을 계속하라고 했다가 다른 아이디어를 검토하게 하는 사이에 성격이 다른 일들이 한 대화에 쌓여 갔다.

나는 개발자로 일하면서 일 잘하는 사람 하나에게 모든 업무를 몰아준다고 조직이 잘 돌아가지 않는다는 것을 여러 번 봤는데, 작업마다 목적이 다르고 알아야 할 내용이 다르며 건드리면 안 되는 것도 달라서 담당이 바뀌어도 일을 이어 갈 수 있게 해 두어야 하기 때문이다. AI 에이전트에게 실제로 일을 맡겨 보니 같은 문제가 그대로 나타났다.

대화창 하나에 일을 계속 쌓으면

1장에서 본 대로 나는 계산기와 테스트 페이지로 흘러간 서비스를 전부 내리고 커뮤니티의 글을 모아 관심사를 분석하는 쪽으로 방향을 바꿨는데, 그 일을 누구에게 시키느냐가 문제였다. 당시 주로 대화하던 세션은 공모전 자료를 찾고 처리 내역을 관리하고 진행 상황을 확인하는 일을 이미 하고 있었고, 이 세션에 여러 커뮤니티의 글을 수집하고 분석해서 화면까지 만들라고 해도 못 할 것 같지는 않아서 실제로 수집을 시험하기 시작했다.

하지만 한쪽에서는 공모전을 찾고 다른 쪽에서는 커뮤니티 관심사를 분석하는데 거기에 사이트를 바꾸라는 말까지 이어지면 서로 다른 일의 배경이 뒤섞여서 모델이 지금 어느 프로젝트를 하고 있는지 놓치는 순간이 올 것 같았고, 그래서 하던 작업을 멈추게 했다.

다른 세션에게 시킬 거야

2026년 10월 14일 저녁의 일이고, 말은 거칠어도 결정은 분명해서 지금까지 생각한 것은 파일로 남기고 이 세션은 원래 하던 일에 집중하게 하며 새 일은 다른 세션으로 보낸다는 것이었다.

컨텍스트는 에이전트가 지금 하는 일을 이해하려고 참고하는 대화와 자료를 말하는데, 사람도 여러 프로젝트를 한꺼번에 하다 보면 들은 이야기를 섞어 기억하듯이 에이전트도 관련 없는 대화가 길게 쌓이거나 요약을 거쳐 이어지면 작업에 필요한 맥락을 정확히 붙들고 있기 어렵고, 내가 걱정한 것이 그 상황이었다. 다만 다른 세션으로 옮긴다고 문제가 저절로 풀리지는 않았는데, 새로 연 세션은 앞선 세션에서 무슨 일이 있었는지 모르기 때문에 무엇을 하다 멈췄고 어떤 아이디어를 시험하려 했으며 자료가 어느 파일에 있는지를 알려 주어야 했고, 사람을 새로 뽑으면 인수인계를 하듯이 새 세션에도 인수인계가 필요했다.

말로 설명하지 말고 파일을 넘기자

주 세션은 커뮤니티 트렌드 분석에 관한 내용, 곧 수집하려던 정보의 범위와 시도해 본 접근 방법과 확인된 자료의 위치를 마크다운 문서 하나로 정리했고, 나는 새 세션을 열어 그 문서를 넘기면서 이렇게만 말했다.

보고 만들어. 네가 전담이야

지시가 이렇게 짧아도 됐던 것은 앞선 세션에서 하던 이야기가 문서에 들어 있었기 때문이고, 나는 중요한 내용만 넘긴 뒤 그다음부터는 새 담당이 자기 일을 파악하게 했다.

이렇게 나누면 토큰을 아끼는 것 말고도 어느 일이 어느 담당에게 있는지가 갈려서, 공모전에 관한 것은 공모전을 하던 세션에 묻고 사이트 담당은 커뮤니티 수집기를 만들고 대시보드 화면을 고치는 데만 집중할 수 있다. 그렇다고 혼란이 다 없어진 것은 아니어서 그날 밤에는 사이트 작업을 맡긴 세션에 다른 업무도 도와 달라고 했다가 다시 세션끼리 업무를 나눠서 하라고 말을 바꿨고 메시지는 되도록 줄이라는 말까지 남겼는데, 실제로 일을 굴려 보면서 어디까지 맡기고 어디서 가를지를 조정한 것이다.

당시에 내가 시작한 것은 세션을 나누고 담당을 정하고 필요한 내용을 넘겨 주는 일이었을 뿐이고, 그 뒤로 세션이 늘어 세션끼리 메시지를 주고받고 일부 작업을 서브에이전트가 맡으면서 운영이 복잡해졌지만 출발점은 한 창에서 일을 너무 많이 시키는 것 같아 창을 하나 더 연 것이었다.

창을 여러 개 여는 것과 일을 병렬로 시키는 것은 다르다

Claude Code 세션을 둘 열어 놓으면 두 명이 일하는 것처럼 보이고 실제로 동시에 작업이 진행되기도 하지만, 세션이 둘이라는 것만으로 두 작업이 독립이 되지는 않아서 두 세션이 같은 파일을 고치면 서로의 변경을 덮어쓰고, 한쪽이 사이트를 배포하는 동안 다른 쪽이 오래된 파일로 다시 배포해 버릴 수도 있으며, 그러고도 둘 다 자기 일을 끝냈다고 보고한다. 그래서 세션을 나눌 때는 그 세션이 무엇을 하는지와 함께 무엇을 건드리면 안 되는지를 정해서, 자료를 모으는 담당은 원본을 확인해 정리한 파일을 저장하게 하고 사이트를 고치는 담당은 확인된 자료를 받아 화면에 반영하게 하며 배포는 어느 쪽이 하는지를 못 박아 둔다.

서브에이전트는 새로 켜 둔 독립 세션과 구분해야 하는데, 서브에이전트는 한 세션이 작업을 하다가 특정 임무를 맡겨 부르고 결과만 돌려받는 것이고, 터미널을 여럿 띄워 유지하는 독립 세션은 담당마다 대화와 진행 상황이 따로 이어진다. 내가 쓴 방식에는 이 둘이 섞여 있었고, 어느 쪽이 나은지는 그 업무가 다른 업무와 얼마나 떨어져 있느냐에 달려 있다.

이제는 서비스가 돌아가는 자리도 알아야 했다

화면만 만들 때는 그 화면을 만드는 파일이 어디 있고 사이트가 어느 서버에서 열리는지 몰라도 일이 되지만, 담당을 나누려면 누가 자료를 모으고 누가 화면을 만들고 누가 배포하는지, 장애가 나면 어디부터 볼지를 알아야 한다.

내 사이트의 처음 구조는 단순해서, 개인 홈페이지로 쓰던 GitHub 저장소에 HTML과 CSS를 두고 GitHub Pages로 공개했으며 사 둔 sungprofile.cloud 도메인을 거기에 연결했다. 내용을 바꿀 때는 내 PC에서 파일을 고쳐 커밋하고 푸시했고, 공모전 자료를 다듬는 일도 내 PC에서 해서 그 결과가 정적 페이지의 재료가 됐으니, 방문자가 보는 것은 내 PC의 폴더가 아니라 배포된 페이지다.

Cloudflare는 10월 16일 밤 게시판을 붙이면서 들어왔는데, 글을 받아 저장하는 쪽은 Workers와 D1이 맡았고, 같은 회사의 Tunnel은 밖에서 내 PC의 브라우저에 들어가려고 따로 써 본 것이다. 이 자리들을 알고 나면 사이트가 안 열린다는 말이 푸시가 실패했는지, 도메인 설정이 틀렸는지, Worker가 답하지 않는지로 갈라진다.

담당을 둘로 나누려는 사람에게 이 그림은 곧 권한의 문제가 되어서, 수집 담당에게 배포 권한이 필요한지, 사이트 담당이 원본 자료를 지울 수 있어야 하는지, 배포 전에 누가 결과를 확인하는지를 이 그림 위에서 정하게 된다.

아무 일에나 가장 무거운 모델을 쓰지는 않는다

담당을 나누고 나면 어떤 모델에게 맡길지도 정해야 한다. 방향을 시험하고 뒤집던 초기에는 좋은 모델을 아끼지 않았지만, 정해 둔 형식으로 제목과 링크를 정리하는 일에 복잡한 판단용 모델을 매번 부를 이유는 없었기 때문에 큰 구조를 처음 잡을 때는 Fable을 쓰고, 같은 꼴을 되풀이하는 일은 Sonnet으로 내리고, 판단이 복잡해지면 Opus로 올렸으며, Sonnet이 한 일은 표본을 뽑아 검사했다. 모델은 세션 안에서 /model 명령으로 바꾸고, 그때 쓸 수 있는 모델과 사용량 조건은 요금제마다 다르니 화면에서 확인하면 되며, 이 이야기는 32장에서 다시 나온다.

결국 사장에게 남는 일

화면을 바꾸는 데만 매달리던 동안에는 에이전트에게 이거 만들라고 하면 됐지만, 일을 나누고 나서는 지금 누가 무엇을 맡고 있고 자료는 어디까지 모였으며 사이트 담당은 어떤 파일을 기다리고 있고 어느 변경이 실제로 공개됐는지를 묻게 됐다. 이것을 전부 내 머리로 기억해서 답하는 방식은 담당이 늘수록 버티기 어려워서, 어떤 업무의 처리 현황을 바로 답하지 못하는 것을 보고 장부를 세션이 직접 관리하게 바꾼 적도 있는데, 에이전트가 여럿이라는 것보다 그들이 한 일을 내가 파악할 수 있느냐가 중요해진 것이다. 그래서 인수인계서에는 열심히 했다는 말이 아니라 지금 남아 있는 파일과 작업 상태, 곧 끝난 것과 아직 확인하지 못한 것과 문제가 생겼을 때 돌아갈 자리가 적혀 있어야 하고, 누가 이어받더라도 그것만 읽고 자기 판단을 시작할 수 있어야 한다.

사이트 하나를 만들어 볼 생각으로 시작한 일이 어느새 담당을 나누고 인수인계서를 쓰는 일이 됐고, 개발자 한 명이 혼자 하는 실험이 작은 팀을 운영하는 일과 닮아 갔는데, 그사이에 늘어난 사람은 없었고 바뀐 것은 내가 일을 시키는 방식이었다.

하네스 실습 — 이제 내 서비스에 담당을 둘로 나눠 보자

앞의 두 장에서 독자는 자기 사이트를 하나 만들었다. 지금은 어떤 자료를 보여 주고 어떤 방향으로 운영하고 싶은지도 조금씩 정했을 것이다. 사이트가 아직 남에게 공개되지 않았어도 괜찮다. 이제 같은 프로젝트를 두 개의 담당으로 나눠 보고, 각 담당이 자신의 일이 무엇인지 아는 상태에서 작업을 이어 갈 수 있는지 확인하자.

이번에는 처음부터 다섯 명짜리 팀을 만들지 않는다. 자료 담당 하나, 사이트 담당 하나면 충분하다. 독자는 여전히 사장으로서 어떤 결과를 만들고 무엇을 공개할지 결정한다.

실습 전에는 현재 프로젝트를 정상적으로 열 수 있는지 확인하자. 기존 사이트를 복사하거나 Git 커밋을 남겨, 변경 전 상태로 돌아갈 방법을 준비한다. 다른 세션에서 같은 폴더를 동시에 수정할 수 있으므로 두 담당이 어느 경로를 변경할지 먼저 정해야 한다. 처음에는 자료 담당은 하네스의 넘김/ 폴더처럼 미리 정한 경로만 수정하고, 사이트 담당만 화면과 배포 관련 파일을 바꾸는 식으로 시작하자. 실제 경로명은 현재 프로젝트를 보고 에이전트가 결정하게 한다.

먼저 기존 Claude Code 세션에서 이렇게 말해 보자.

저자

지금까지 만든 내 서비스에서 자료 수집과 사이트 수정이 섞이지 않도록 담당을 두 개로 나누고 싶어. 현재 파일 구조를 조사하고, 자료 담당에게 넘길 인수인계서를 만들어 줘. 지금 완료된 일, 실제 파일 경로, 이번에 해야 할 일, 건드리면 안 되는 파일, 검증 방법을 적어 줘. 기존 코드는 아직 수정하지 마.

이 단계에서는 실제로 존재하는 파일 경로가 적혔는지, 무엇을 이어받을지 알 수 있는지를 본다. '서비스를 잘 만들어 주세요' 정도의 추상적인 문서라면 다시 고쳐 달라고 하자.

내 폴더에서 세션은 두 담당이 만나는 자리를 표 한 장으로 잡았다. 자료 담당은 새 표까지만 만들고, 원본을 새 표로 바꿀지는 내가 승인하며, 화면 반영은 그다음에 사이트 담당이 한다. 인수인계서의 '건드리면 안 되는 것' 항목에는 빌드 명령이 배포용 폴더를 덮어쓴다는, 그날 세션이 직접 겪은 일이 적혀 있었다.

문서가 생겼다면 새 터미널 또는 새 Claude Code 세션을 연다. 같은 프로젝트를 작업하되 새 세션은 자료 담당이라고 정한다. 만약 하네스에 별도 에이전트 생성 기능이나 역할 파일이 이미 있다면 이를 활용해도 된다. 하지만 그 기능이 현재 버전에 없다면 '나중에 만들겠다'고 해 놓고 실제로 실행된 것처럼 넘어가지 말자. 새 Claude Code 세션에서 문서를 읽고 작업하게 하는 것만으로도 이번 실습의 핵심을 경험할 수 있다.

저자

너는 이 프로젝트의 자료 담당이야. 앞선 세션이 작성한 인수인계 Markdown을 읽고 현재 자료가 어디에 있는지부터 확인해 줘. 앞에서 고른 자료를 읽어 중복·빈 값·링크 오류를 확인하고 결과를 별도 보고서로 남겨. 사이트 화면과 배포 파일은 수정하지 마. 필요한 자료가 없으면 없는 그대로 보고해 줘.

새 세션은 인수인계서만 읽고 표의 문제 네 건을 줄 번호와 함께 다시 찾아냈다. 인수인계서가 만들라고 한 새 표는 만들지 않았다. 어느 도서관을 다룰지 내가 아직 정하지 않았기 때문이라고 했다.

이제 기존 세션은 사이트 담당으로 남긴다. 이 담당에게는 자료 수집을 다시 시키지 않는다. 자료 담당이 만든 보고서를 읽고, 화면에서 어떤 것을 고쳐야 할지 제안하게 한다. 두 담당이 실제로 같은 결과물을 향해 움직이지만 서로 다른 파일을 고치고 있는지 확인하자.

저자

너는 사이트 담당이야. 자료 담당이 만든 검증 보고서를 확인하고, 지금 사이트에서 무엇을 바꾸면 좋은지 두 가지 제안해 줘. 내가 선택하기 전에는 공개 배포하지 마. 다른 담당의 수집 파일은 덮어쓰지 말고, 화면 관련 파일만 수정해.

독자가 잠깐 다른 일을 하다가 돌아왔을 때, 어느 담당이 무슨 일을 했고 어떤 파일을 바꾸었는지 답을 얻을 수 있어야 한다. 두 작업이 같은 파일을 고치려 한다면 일단 멈추고 수정 권한을 다시 나눠 보자.

사이트 담당은 보고서를 원본 표와 화면에 다시 맞춰 본 뒤, 보고서에 없던 것을 하나 찾아냈다. 요일이 빈 '초등 과학 실험' 카드는 '언제'에서 무엇을 골라도 화면에서 사라진다는 것이다. 코드를 읽고 확인했을 뿐 단추를 직접 눌러 보지는 않았다고 밝혔다.

### 자료 담당의 모델을 바꿔 보기

이번에는 자료 담당 세션에 돌아가 /model을 입력하자. 선택 가능한 모델을 확인하고, Sonnet이 제공된다면 이번처럼 정해진 형식으로 자료를 읽고 확인하는 반복 작업에 적용해 보자. Opus로 작업했을 때와 결과를 비교하고 싶다면 작은 표본을 먼저 정해 같은 입력으로 확인해 볼 수 있다. 단, 서로 다른 모델을 똑같은 자료에 적용하려면 파일 상태와 지시 조건을 고정해 둬야 비교가 의미 있다.

저자

이번 수집·정리 작업은 반복 성격이 강해. 현재 모델과 사용 가능한 모델을 확인하고, Sonnet으로 작업하기 적절한지 설명해 줘. 모델 변경은 내가 직접 확인할게. 같은 자료 20건을 정해 제목·출처·날짜·중복 여부를 검사하고, 확실하지 않은 값은 추측하지 말고 표시해 줘. 결과를 파일로 남겨 줘.

모델을 바꿨다고 무조건 더 빨라지거나 저렴해지는 것은 아니다. 요금제의 사용 제한, 모델별 작업 정확도, 재검증 비용에 따라 선택은 달라진다. 이번 장에서는 *반복 업무를 항상 가장 높은 모델에 맡길 필요는 없다*는 판단을 직접 실험해 보는 것으로 충분하다.

### 이제 내 서비스가 어디서 돌아가는지도 확인하자

마지막으로 사이트 담당에게 현재 프로젝트의 인프라 구성을 설명해 달라고 요청해 보자. 이때 내 서비스의 실제 구성과 이 책에 등장한 sungprofile.cloud의 과거 구성을 혼동하지 말자. 독자의 하네스가 임시 URL이나 다른 배포 서비스를 사용하고 있다면 그것을 있는 그대로 그리면 된다.

저자

지금 내 사이트가 어느 파일에서 만들어지고, Git 저장소는 어디이며, 어디에 배포되는지 실제 설정 파일을 확인해서 설명해 줘. 데이터가 어디에 저장되는지도 구분해 줘. 확인한 사실만으로 간단한 구조도를 만들고, 확인하지 못한 설정은 미확인이라고 적어 줘. 외부 배포나 DNS 설정은 지금 바꾸지 마.

이번 장이 끝났을 때 남아야 할 것은 독립적으로 이어받은 자료 담당 세션 하나, 사이트 담당 세션 하나, 실제 파일 경로가 적힌 인수인계서 하나, 서비스 인프라 지도 하나다. 자료 담당을 Sonnet으로 바꿨다면 표본 검증 기록도 남겨 두자.

다음에는 담당을 나누었다는 사실보다 그 담당들이 실제로 만든 결과를 어떻게 확인할지가 중요해진다. 둘이 동시에 일했다고 해서 두 배로 정확해지는 것은 아니니까.
