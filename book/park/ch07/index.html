7장. 서비스 배포와 공개 운영

에이전트가 파일을 만들고 테스트를 통과시키고 브라우저에서 화면까지 보여 주면 기분은 좋지만, 그 화면이 내 컴퓨터에만 떠 있는 동안에는 창을 닫으면 끝이고 친구에게 보여 주려 해도 캡처를 떠야 하며, 그것이 좋은지 나쁜지를 가리는 데 필요한 남의 반응은 한 번도 받지 못한 상태다. 서비스를 만들기 시작하던 무렵에 나는 대단한 배포 계획을 세우지 않았는데, 여기서부터 클라우드 엔지니어가 되어야 한다면 사이트 하나를 빨리 만드는 재미가 그날로 끝날 것이기 때문이고, 그렇다고 남에게 보여 줄 수 없는 코드를 계속 쌓아 두고 싶지도 않아서 만들었으면 일단 인터넷에 올려 보고 결과가 이상하면 고치기로 했다.

다만 인터넷에 내놓는 순간부터는 책임이 따라서, 저장하면 안 되는 개인정보를 저장하고 있지 않은지와 API 키가 파일에 남아 있지 않은지, 공개하면 안 되는 수집 자료가 섞여 있지 않은지를 확인해야 하고, 공개하기 전에 반드시 봐야 하는 것과 공개한 뒤 반응을 보며 바꿔도 되는 것을 나눠 두어야 한다.

주소 하나 사 놓은 게 떠올랐다

지금 쓰는 서비스는 2026년 10월 13일 저녁 저장소에 Personal homepage라는 커밋이 생기면서 개인 홈페이지로 출발했고, 다음 날 계산기와 작은 서비스들이 붙었다가 다시 지워졌다. 그 사이인 10월 14일 오후 3시 50분에 나는 Claude에게 이렇게 말했다.

저자

그 깃허브 보면 내 포트폴리오용으로 사 놓은 도메인 있거든

나는 주소를 갖고 있다는 사실만 말했고 그것을 어떻게 연결할지는 에이전트가 알아낼 일이었는데, 에이전트는 내 GitHub 저장소들을 뒤져 예전 포트폴리오의 주소와 설정을 찾아냈다고 보고하면서 sungprofile.cloud에 HTTPS로 접속하면 오류가 난다는 것도 함께 알렸고, 2분 뒤인 15시 52분에는 저장소에 Create CNAME이라는 커밋이 남았다. 도메인이 있다는 것과 그 도메인으로 안전하게 접속된다는 것은 다른 문제여서 처음부터 말끔하게 연결되지는 않았다. 에이전트는 파일 하나를 저장하고 연결했다고 말하기 쉽지만 실제로는 DNS 설정과 GitHub Pages 설정, 인증서 발급, 브라우저 접속이 저마다 다른 단계이고, 어느 하나가 끝났다고 나머지까지 끝났다고 믿으면 내가 보는 화면과 방문자가 보는 화면이 달라진다.

지우는 일이 안전해야 과감히 지울 수 있다

나는 사이트를 며칠 사이에 여러 번 갈아엎었는데, 그동안 만든 코드가 아깝지 않으냐고 묻는다면 방문자가 원하지 않는 것을 정성껏 붙잡고 있는 편이 더 아깝다고 답하겠다. 다만 그러려면 버리는 일이 안전해야 해서, 작업 폴더의 파일을 덮어쓰기만 하면 어제 무엇을 만들었는지를 기억에 기대야 하지만 Git에는 어느 시점에 무엇이 바뀌었는지가 남고, 옛 코드를 되살릴 생각이 없더라도 돌아갈 수 있다는 사실만으로 더 과감하게 바꿀 수 있다. 10월 14일 저녁 7시 42분에 저장소에 생긴 ‘서비스 전부 내림’ 커밋(f31c07e9703)이 그런 경우여서, 사람들이 무엇에 관심을 두는지 보지도 않고 서비스를 여러 개 만든 것이 문제라고 느껴 지웠지만 지운 것이 이력에 그대로 남아 있으니 망설일 일이 없었다.

10월 16일, 첫 화면의 주인이 바뀌었다

10월 16일 오후 1시 40분에 사이트 담당 세션에 바탕화면의 공모전 자료로 사이트를 싹 바꾸라고 지시한 일은 2장부터 4장까지에서 다뤘으니, 여기서는 이미 공개돼 있던 서비스의 첫 화면이 바뀐 과정만 본다. 지시 4분 뒤인 오후 1시 44분의 커밋(ef30c908b83)에서 루트 화면이 공모전 서비스로 바뀌고 기존 홈은 /lab으로 옮겨졌으며, 1시 48분의 커밋(a68a3031be4)에서 사이트 전체가 공모전 정보 중심으로 넘어갔으니, 사람들이 이미 들어올 수 있는 주소의 메인 화면이 8분 사이에 바뀐 셈이다. 그보다 앞선 1시 34분에 공모전 데이터 737건을 갱신한 커밋이 있지만 이것은 1시 40분 지시의 결과가 아니라 그 전부터 돌던 데이터 갱신이고, 첫 화면 변경이 그 뒤를 이었다.

GitHub에 올렸다는 말과 배포됐다는 말

GitHub는 코드를 보관하고 변경 이력을 관리하는 곳이고 GitHub Pages는 그 저장소의 정적 사이트를 인터넷에 내보내는 기능이어서, 둘을 이어 쓰기는 해도 저장소의 코드가 바뀌는 순간 방문자의 화면이 따라 바뀌는 것은 아니다. 에이전트가 파일을 고치면 로컬 파일이 바뀐 것이고, 커밋하면 로컬 저장소에 변경 기록이 남은 것이며, 푸시하면 원격 저장소에 그 변경이 전달된 것이고, GitHub Pages가 빌드와 게시를 끝내야 배포가 된 것이며, 마지막으로 공개 주소에서 새 화면이 뜨고 핵심 기능이 작동하는 것을 확인해야 내가 뜻한 변경이 방문자에게 닿았다고 말할 수 있다.

회사 일에 견주면 파일을 고친 것은 내 컴퓨터에서 보고서를 고친 것이고, 커밋은 수정 이력에 남긴 것, 푸시는 공동 문서함에 올린 것, 배포는 사람들이 읽는 공식 게시판에 붙인 것, 마지막 확인은 게시판에 가서 제대로 보이는지 살펴본 것에 해당하니, 보고서 파일을 저장했다고 전체 공지가 된 것이 아님은 누구나 안다. Git 명령어를 외울 필요는 없고 Claude Code나 Codex에게 실행하게 하되, 다섯 단계 가운데 어디까지 끝났고 어디는 아직 확인하지 않았는지를 설명하게 하면 된다.

도메인과 호스팅은 다른 문제였다

sungprofile.cloud라는 주소를 샀다고 그 안에 서버가 들어 있지는 않다. 도메인은 어디로 찾아갈지를 알려 주는 이름이고 호스팅은 요청이 왔을 때 실제 화면을 돌려주는 자리이며, 둘을 잇는 것이 CNAME이라는 DNS 기록이다. 정적 파일은 GitHub Pages가 서버 관리 없이 내보내 주었고, 방문자가 글을 쓰는 기능이 필요해진 뒤에야 8장에서 볼 Workers와 D1이 붙었다.

인증서 오류가 보이면 아는 척하지 말 것

도메인을 연결하던 중에 에이전트가 HTTPS 오류를 보고했다. 설정을 바꾼 직후라 DNS가 아직 퍼지지 않았을 수도 있고 GitHub Pages 쪽 인증서가 준비되지 않았을 수도 있는데, 에이전트의 보고가 '접속이 안 되니 다시 배포하면 됩니다' 한 문장으로 끝나면 나는 문제가 고쳐진 것인지 알 길이 없다. 그래서 추정은 추정이라고 말하게 하고, CNAME 파일이 있는지, DNS가 어디를 가리키는지, Pages 설정에 등록된 도메인이 무엇인지, 인증서가 발급됐는지를 하나씩 확인해 오게 했으며, 권한이 없어 확인하지 못한 것은 못 했다고 적게 했다.

배포를 에이전트에게 맡겨도 최종 판단은 내 몫이다

보안도 확인하고 배포도 검증하고 오류가 나면 로그까지 읽어야 한다면 개발자가 아닌 사람은 이 일을 어떻게 하느냐고 물을 수 있는데, 기술적인 세부는 에이전트에게 맡기고 사람은 무엇이 해결됐고 무엇이 아직 해결되지 않았는지를 가리면 된다. 다만 개인정보를 다루는 기능이나 유료 결제에 얽힌 기능, 비밀키가 공개 저장소에 올라가는 일처럼 잘못되면 피해가 큰 것은 실험이라는 이름으로 넘길 수 없으므로, 얼마든지 되돌릴 수 있는 화면 수정은 빠르게 하되 되돌리기 어려운 정보 공개와 권한 변경에는 내 승인을 거치게 해 둔다.

하네스 실습 — 내가 만든 사이트를 실제 인터넷에 공개해 보기

앞 장까지 독자는 사이트를 만들고, 자료를 모으는 담당을 나누고, 반복되는 수집을 스크립트로 돌리는 일을 경험했다. 이제 그 결과를 다른 사람에게 보여 줄 차례다. 여기에서 처음부터 복잡한 서버를 구성할 필요는 없다. Vercel에 가입하거나 로그인하지 않은 채 1장을 끝냈다면 하네스가 내준 임시 주소는 60분 뒤 사라진다. 이번에는 사라지지 않는 주소를 만든다. 하네스로 만든 사이트라면 가장 빠른 길은 세션에 '올려'라고 하는 것이다. 이미 다른 호스팅을 사용하고 있다면 괜히 전부 옮기지 말고 현재 구조가 어떻게 배포되는지 확인하는 것으로 시작하면 된다.

처음에는 이렇게 부탁하면 된다.

저자

내 프로젝트를 보고 지금 어떤 방식으로 실행·배포되는지 확인해. 인터넷에 공개하려면 무엇을 해야 하는지 네가 알아보고, 현재 확인된 것과 확인하지 못한 것을 구분해서 알려 줘. 비용이 드는 선택이나 기존 서비스 설정을 변경하는 일은 먼저 설명해.

세션의 첫 문장은 이 사이트가 내 PC 안에서만 돌고 있고 인터넷에 올린 기록이 없다는 것이었다. 공개하는 길로는 하네스의 올리기 명령을 들었다. 내 PC에서 빌드한 것을 Vercel에 올려 임시 주소부터 받는 방법이다. 지금 그대로 올리면 집계 화면과 시험 화면까지 함께 공개된다는 것, Vercel 무료 플랜은 비상업 용도만 허용한다는 것을 미리 말했다. 틀린 설명도 하나 섞여 있었다. 폴더에 남아 있던 하네스 저장소의 자동 빌드 설정을 내 사이트가 나가는 둘째 길로 소개했는데, 확인해 보니 그 설정은 내 사이트와 상관이 없었다.

### 먼저 저장소에 무엇이 있는지 확인하기

에이전트가 나에게 설명해야 할 최소한의 정보는 네 가지다. 무엇을 실행해야 화면이 만들어지는지, 어디에 그 파일이 생기는지, Git으로 관리 중인지, 공개해도 되는 파일만 들어 있는지다. 파일이 많고 코드가 낯설어도 상관없다. 에이전트가 찾은 근거를 설명하면 된다. 예를 들어 package.json에 빌드 명령이 있다면 그 위치를 말하고, 빌드된 폴더가 어디인지 알려 주면 된다. 정적 HTML로만 구성돼 있다면 빌드 과정이 없어도 된다.

먼저 볼 명령어는 git status다. 이것은 현재 작업 디렉터리에서 Git이 무엇을 변경된 파일로 보고 있는지 확인할 때 쓰는 명령이다. 직접 입력해도 되고 에이전트에게 실행시켜도 된다. 배포 전에는 에이전트가 이 결과를 읽고 어떤 파일이 바뀌었는지 말할 수 있어야 한다. 저장소 밖에 있던 비밀키가 실수로 추적되기 시작했다면 이 단계에서 막아야 한다.

다음은 git diff다. 이전 상태와 무엇이 달라졌는지를 보여 준다. 코드가 수천 줄이더라도 사람이 전부 외울 필요는 없다. 에이전트에게 배포 관련 변경만 요약하고, 예상하지 못한 수정 파일이 있는지 확인해 달라고 하면 된다. 설정을 무리하게 건드리거나 데이터 파일을 삭제한 흔적이 있다면 그 이유를 먼저 물어보면 된다.

### '올려'로 계속 쓰는 주소 받기

세션에 '올려'라고 한다. 올리는 일이 끝나면 출력에 '계속 쓰는 주소'가 나온다. 그 주소를 브라우저로 열어 Vercel에 가입한다. 가입과 로그인은 내가 직접 한다. 가입을 마친 뒤 다음번 '올려'부터는 사라지지 않는 vercel.app 주소로 올라간다. 이미 Vercel에 로그인된 컴퓨터였다면 1장에서 받은 주소가 처음부터 그 주소다. 처음에는 개인 실험용 사이트로 연습하는 편이 안전하다.

에이전트에게 ‘공개 가능한 최소 상태’를 만들라고 말해 보자. 아직 도메인이 없어도 된다. Vercel이 제공하는 기본 주소로 사이트가 열리는지부터 확인하면 된다. 정적 호스팅은 서버에서만 동작하는 API나 비밀 환경변수를 브라우저로 자동 전달해 주는 도구가 아니다. 서버 기능이 필요한 경우에는 추가 인프라가 필요하다는 점을 에이전트가 설명해야 한다.

### 도메인 연결을 해보고 싶다면

이미 도메인이 있다면 sungprofile.cloud처럼 그 주소를 연결할 수 있다. 없다면 이번 장에서 굳이 새 도메인을 구입할 필요는 없다. 먼저 기본 주소로 사이트가 정상 공개되는 경험을 얻는 것이 목적이다. 도메인을 연결하는 경우에는 자신의 DNS 관리 서비스에서 설정할 권한이 필요한데, 에이전트가 레코드 변경을 제안하면 현재 값과 변경할 값, 되돌리는 방법을 함께 설명하게 한다.

실습에서 바꿀 수 있는 것은 자기 계정의 DNS뿐이다. 다른 사람이 쓰는 도메인을 건드리거나, 이전 서비스를 운영 중인 주소를 검토 없이 덮어쓰면 안 된다. 사용자 지정 도메인을 설정한 뒤에는 DNS 조회가 되는지, Vercel이 도메인을 받았는지, HTTPS 접속이 되는지 구분해서 확인한다. 이 중 하나라도 실패하면 ‘완료’로 표시하지 않는다.

### 정말 배포됐는지 확인하고, 한 번 바꿔 보기

이제 가장 중요한 단계다. 에이전트가 배포에 성공했다고 보고했으면 브라우저에서 공개 주소를 열어 본다. 한 번 열리는 데서 끝내지 말고, 작은 변경을 하나 더 해 본다. 예를 들어 사이트 소개 문구를 한 줄 바꾸거나, 목록 화면의 제목을 조금 바꾸어도 된다. 이 작은 변경을 하고 다시 '올려'라고 한 뒤 실제 URL에서 바뀌었는지 확인하게 한다. 이때 변경 전후 화면을 같이 저장하면 어느 단계에서 문제가 생겼는지 찾기 쉽다.

사이트가 업데이트되지 않았다면 그 이유를 에이전트에게 설명하게 한다. '올려'의 출력에 새 주소가 나왔는지, 배포 작업이 성공했는지, 사이트가 이전 내용을 보여 주는지 따로 확인한다. 한꺼번에 모든 설정을 바꾸기보다 실패한 단계를 찾는 편이 빠르다. 그 과정에서 내가 모르는 기술 용어가 나오면 그때 물어보면 된다.

이 장의 마지막 실습은 변경을 되돌리는 방법을 설명받는 것이다. 1장의 '되돌려 줘'는 하네스가 남긴 스냅샷으로 돌아가는 것이고, 여기서 말하는 Git 되돌리기는 그와 별개의 장치다. Git에는 과거 기록을 보는 방법이 있고, 이전 버전을 기준으로 다시 배포할 수도 있다. 하지만 이미 공유된 저장소에서 기록을 무조건 강제로 되감는 행동은 위험하다. 에이전트에게 어떤 변경을 되돌릴지 정확하게 조사하게 하고, 새 커밋으로 변경을 취소하는 방식을 우선 검토하게 한다. 독자는 실제 운영 사이트에서 무작정 reset --hard나 강제 푸시를 연습할 필요가 없다. 실습용 브랜치나 별도 저장소에서 충분히 확인할 수 있다.

Codex를 쓴다면 변경한 파일의 diff를 검토하고 코드 리뷰를 요청할 수 있다. Claude Code를 쓴다면 같은 Git 변경 기록을 읽고 공개 사이트와 일치하는지 점검하게 하면 된다. 한쪽이 만든 변경을 다른 쪽에 검토하도록 맡길 수도 있지만 처음부터 두 도구를 모두 사용할 필요는 없다. 중요한 것은 현재 어떤 상태인지 알고 수정할 수 있는가이다.

### 이번 장에서 남길 것

실습이 끝나면 독자의 프로젝트에는 인터넷에서 열리는 주소 하나와 변경 이력이 남아야 한다. 어떤 변경이 공개 사이트에 반영됐는지, 실패하면 어디부터 확인할지, 공개하면 안 되는 파일을 어떻게 구분했는지는 설명할 수 있어야 한다. 이것이 이번 장에서 얻을 운영 능력이다.

나는 이미 가진 도메인이 있으니 찾아보라고 했고, 사이트를 만들어 공개했으며, 틀린 방향은 고쳐 나갔다. 실제 주소를 가진 서비스가 됐다는 사실이 무엇보다 중요했다. 만든 것이 세상 밖에 나와야, 다음에 무엇을 바꿔야 할지도 보인다.
