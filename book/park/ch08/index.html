8장. 병렬 작업 환경의 구성

회원가입을 붙이고 게시판 하나를 만들고 싶다는 생각이 들면 설계도가 갑자기 복잡해져서 프론트엔드, 백엔드, 데이터베이스, 웹 서버, WAS 같은 이름이 줄줄이 등장하고, 어제까지 브라우저에서 잘 열리는 사이트를 만들던 사람이 서버실이라도 차려야 할 분위기가 된다. 이 장은 내가 그 자리에서 서버를 따로 두지 않기로 한 날의 이야기이고, 그 판단에 필요했던 만큼만 프로그램이 일하는 방식을 짚는다.

나는 일단 게시판을 만들고 싶었을 뿐이었다

2026년 10월 16일 오후 8시 18분에 나는 사이트 담당 세션에 이렇게 말했다.

저자

회원가입 기능도 만들고 커뮤니티 기능도 대충 만들어. 해당 공모전 후기 게시판 형식으로

공모전 정보를 보여 주는 페이지는 이미 인터넷에 올라가 있었으니 그것을 본 사람들끼리 후기를 남기고 정보를 주고받을 자리가 있으면 좋겠다는, 막 돌아가기 시작한 사이트에 기능 하나를 붙여 보자는 정도의 생각이었다. 세션은 데이터베이스와 서버가 필요하다고 보고 여러 선택지를 만지기 시작했고 나도 Vercel의 서버리스 함수에 MongoDB를 붙이는 쪽을 잠깐 입에 올렸지만, 2분 뒤인 8시 20분에 말을 바꿨다.

저자

애초에 애드센스도 안 붙었는데 그냥 클라우드플레어 CDN으로 처리하자. 귀찮다

지금 봐도 솔직한 운영 판단이었다고 생각한다. 광고조차 붙지 않은 서비스에서 내가 얻으려던 것은 서버를 운영해 보는 경험이 아니라 후기 게시판이 정말 필요한지, 사람들이 쓰기는 하는지를 알아보는 것이었고, 수익도 이용자도 확인되지 않은 서비스에 오래 떠안을 운영 부담을 미리 얹고 싶지 않았다.

그날 밤 9시 32분에 jupjup-api라는 Cloudflare Worker와 D1 데이터베이스를 연결한 커밋이 생겼다. 정적 사이트를 GitHub Pages로 보여 주는 구조는 그대로 두고 글을 등록하고 조회하는 것처럼 서버 쪽에서 실행해야 하는 부분만 Worker로 보내며 데이터는 D1에 쌓는 구성이다. 상시로 띄워 두는 서버를 만들지 않았을 뿐이지 방문자의 요청을 받아 처리하는 프로그램과 데이터베이스가 없어진 것은 아니고, 서버 프로세스를 살려 두고 돌보는 책임의 대부분을 서비스 제공자에게 넘긴 것인데, 작은 서비스일수록 이 차이가 크다.

게시판 하나에 필요한 것

이미 만들어 둔 HTML과 이미지를 그대로 보내 주기만 하는 사이트라면 정적 파일을 전달하는 호스팅과 CDN으로 충분하고, 내 사이트의 처음 모습이 그랬다. 방문자가 게시판에 글을 쓰고 등록을 누르는 순간부터는 누군가 그 글을 받아 로그인했는지 확인하고 입력을 검사해 데이터베이스에 저장해야 하는데, 이런 일을 맡는 프로그램을 WAS라고 부른다. WAS도 운영체제 위에서 프로세스로 도는 프로그램일 뿐이어서, 요청이 여럿 들어오면 일을 번갈아 처리하거나 여러 코어에 나눠 처리한다.

여기서 갈리는 것은 그 역할이 필요하다는 것과 그 프로그램을 내가 24시간 직접 띄워 두어야 한다는 것이 같은 말이냐는 점이다. 운영체제를 패치하고, 프로그램이 죽으면 다시 띄우고, 사람이 늘면 서버를 키우는 일까지 떠안지 않아도, 요청이 올 때만 실행되는 서버리스 플랫폼에 그 역할을 넘길 수 있다.

Claude Code가 '백그라운드에서 한다'는 말도 정확히 봐야 한다

에이전트가 '백그라운드로 돌리겠습니다'라고 할 때 뒤에서 도는 것은 네 가지 가운데 하나다. Claude Code가 셸 명령을 뒤로 돌려 둔 것이라면 도는 것은 스크립트이고 그동안 모델은 추론하지 않는다. 서브에이전트를 띄운 것이라면 다른 에이전트가 파일을 읽고 판단하므로 사용량이 든다. 운영체제의 작업 스케줄러에 걸어 둔 것이라면 Claude가 꺼져 있어도 정해진 시각에 프로그램이 돈다. 마지막으로 사이트의 Worker는 개발을 돕는 에이전트가 아니라 방문자의 요청을 처리하는 프로그램이어서, 방문자가 글을 남긴다고 Claude 세션이 깨어나지는 않는다.

이름은 다 백그라운드여도 누가 무슨 프로그램을 어느 자원으로 돌리는지가 다르고, 그것을 묻지 않으면 비용도 성능도 가늠할 수 없다.

'에이전트들 다 날려'라고 하면서 자동화는 남겨 두었다

그 구분이 가장 선명하게 드러난 날이 6장에서 본 10월 17일 아침이다. 그날 엉킨 것은 화면을 만지는 작업이었고, 그때 나는 이런 말도 했다.

저자

그냥 네가 직접 해, 하나씩. 오히려 꼬인다

내가 싫었던 것은 나눠 놓은 작업들이 같은 자원을 놓고 부딪히고, 나는 지금 무엇이 되고 있는지 알 수 없는데 모델 사용량만 늘어나는 상황이었다. CPU로 하는 계산이나 파일 수집처럼 서로 간섭할 일이 적은 작업은 한꺼번에 돌려도 되지만 마우스 하나를 움직여야 하는 화면 작업은 여러 세션이 먼저 하겠다고 덤비면 빨라지기는커녕 막혀 버리기 때문에, 멈추게 한 것은 엉킨 화면 작업과 쓸데없이 돌던 에이전트뿐이고 뒤에서 도는 작업은 계속 돌렸다. 화면을 다투는 일과 뒤에서 도는 일을 가르는 것이 이번 장의 병렬 처리 이야기와 만나는 자리다.

20분마다 수집한 프로그램은 누구의 일이었을까

6장의 수집기는 운영체제의 작업 스케줄러가 20분마다 돌렸고, Claude는 그 프로그램을 처음 만들 때와 결과가 이상해졌을 때만 불렀다.

다만 앞선 실행이 끝나기 전에 다음 실행이 시작되면 쓰던 파일을 덮어쓰거나 같은 글을 두 번 넣게 되므로, 되풀이 실행에는 겹쳐 돌지 않게 막는 장치와 실패 로그, 재시도 횟수 제한, 이미 처리한 자료를 알아보는 표시가 있어야 하고, 그것이 실제로 지켜지는지는 시험으로 확인한다.

그래서 나에게 필요한 것은 '서버 전문가'가 아니라 구조를 질문할 수 있는 능력이었다

후기 게시판을 붙이겠다고 했을 때 내게 필요했던 질문은 어떤 프레임워크가 가장 좋으냐가 아니라 방문자가 무엇을 저장해야 하고 어떤 요청이 들어오며 지금 단계에서 어디까지 운영할 것이냐였고, 정적 페이지로 충분한 부분은 정적으로 둔 채 쓰기 요청을 처리하는 부분만 Worker로 만든 것은 그때의 목적에 맞는 선택이었으며 방문자가 늘고 기능이 복잡해지면 그때 구조를 다시 따져 보면 된다. 물론 Workers와 D1에도 한도가 있어서 10월 19일에는 D1 읽기량이 하루 제공량에 가까워졌다는 보고가 올라왔는데, 방문 통계를 조회할 때마다 너무 많은 행을 되풀이해 읽는 구조가 원인이었다. 서버를 직접 설치하지 않았더라도 잘못 짠 쿼리는 비용과 한도 문제를 만든다.

하네스 실습 — 내 사이트는 누가, 언제, 어디서 처리하는가

이번 실습의 결과물은 독자 자신의 서비스에 실행 구조를 그려 보고, 꼭 필요한 동적 기능 하나만 설계·구현해 보는 것이다. 1장에서 만든 서비스를 계속 사용한다. 처음부터 모든 계정을 개설하거나 돈을 내지 말자. 현재 무료 호스팅이나 로컬 실행으로 가능한 수준부터 검증한다.

먼저 Claude Code에서 기존 프로젝트를 열고 이런 취지로 말해 보자.

저자

지금 프로젝트에서 브라우저가 직접 실행하는 부분, 파일 생성 스크립트가 실행하는 부분, 외부 요청을 받아 처리해야 하는 부분을 찾아서 실제 파일 경로와 함께 설명해. 프로세스·스레드·백그라운드 작업이 어디에 해당하는지도 구분해. 아직 확인하지 못한 것은 추측이라고 표시하고, 이 서비스를 운영하는 데 상시 WAS가 꼭 필요한지 대안별로 비교해 줘. 결론을 정하기 전에 나에게 설명해.

여기서 독자가 확인할 첫 번째 것은 코드가 아니라 에이전트의 설명이다. '우리 사이트는 마이크로서비스가 좋습니다' 같은 말만 하면 왜 그런 결론이 나왔는지 다시 묻는다. 실제 코드에서 방문자 입력을 데이터베이스에 저장하는 경로가 있는지, 단순히 정적 JSON 파일을 읽기만 하는지, 어떤 데이터가 외부 방문자에게 공개되어도 되는지부터 확인한다. 모르는 상태에서 멋있는 이름으로 설계를 시작하면 앞서 겪은 계산기 사건을 다시 겪게 된다.

내 사이트에서는 거르기 단추가 브라우저 쪽이었다. 카드 아홉 장은 이미 HTML에 들어 있고 단추는 보이기와 숨기기만 한다. 표를 사본으로 옮기고 화면 파일을 만드는 일은 스크립트 쪽이었다. 상시 WAS에 대해서는 네 가지 방법을 비용과 운영 부담으로 견준 뒤 지금 기능만 보면 필요한 곳이 없다고 했다. 결론은 내리지 않고 세 가지를 물었다. 방문자가 무언가를 보내게 할 것인지, 자료를 얼마나 자주 바꿀 것인지, 나중에 수익을 낼 것인지.

다음으로 아주 작은 실험을 한다. 파이썬 스크립트 하나를 만들어 한 번은 전면에서 실행하고, 한 번은 백그라운드에서 실행한다. 다른 창에서 로그가 갱신되는지 확인한다. 이어 독립적인 테스트 스크립트 두 개를 동시에 실행하고, 두 스크립트가 같은 파일에 쓰도록 했을 때 결과가 왜 꼬일 수 있는지 관찰한다. 실제 서비스 데이터는 사용하지 않는다. 테스트용 임시 파일만 쓴다. 독립 작업을 병렬로 실행하는 것과 공유 자원을 잘못 건드리는 것은 다르다는 사실을 체험하는 과정이다.

이제 사이트에 실제로 필요한 동적 기능이 무엇인지 정한다. 예컨대 방문자가 의견을 남기는 기능이 있다면, 댓글 원문을 데이터베이스에 저장하기 전에 입력 검증과 개인정보 처리 방침부터 확인해야 한다. 처음 실험이라면 게시글 공개 기능 대신 공개되지 않는 테스트 카운터나 간단한 피드백 접수 API처럼 범위가 작고 민감정보를 요구하지 않는 기능을 골라도 된다. 로컬에서 요청과 응답을 확인한 다음, 필요할 때만 서버리스 Worker를 배포한다. 공개 API에는 남용 방지와 입력 제한을 반드시 둔다.

마지막으로 프로젝트 안에 짧은 실행 구조 문서를 남긴다. 정적 페이지는 어디에서 배포되는지, 수집 스크립트는 누가 언제 실행하는지, 외부 요청은 어디에서 처리하는지, 데이터는 어디에 저장되는지, 서로 동시에 실행해도 안전한 작업과 순서를 지켜야 하는 작업은 무엇인지 적는다. Claude가 제안한 구조를 그대로 정답으로 확정하지 말고, 실제 코드와 대조한 뒤 남긴다. 나중에 새 세션을 열 때 이 문서가 있으면 어느 담당이 무슨 자원을 만질 수 있는지 설명하기가 쉬워진다.

이 장을 끝낸 독자는 이제 '에이전트를 병렬로 돌려 보세요'라는 말을 조금 다르게 들을 것이다. 백그라운드에서 실행되는 파이썬 프로그램과 Claude의 서브에이전트, 웹 방문자 요청을 처리하는 Worker, Windows 작업 스케줄러에 등록한 작업은 모두 같은 기술이 아니다. 서로 다른 실행 주체가 동시에 일하면서 하나의 서비스를 구성할 수 있을 뿐이다. 이 차이를 이해해야 작업을 더 많이 시키는 일이 아니라, 무엇을 동시에 돌려도 되고 무엇은 순서를 지켜야 하는지 결정하는 일이 가능해진다.

내가 혼자 여러 역할을 수행한다는 것도 같은 이야기다. 한 사람이 하루 종일 모든 일을 직접 계산할 수는 없다. 대신 한 번 판단해 둔 규칙은 프로그램이 반복하게 하고, 새로 모르는 문제가 나타나면 에이전트가 조사하게 하고, 서로 간섭하는 작업은 순서를 정하고, 방문자 요청은 적합한 서버 기능이 받게 만든다. 복잡해 보이던 서버와 병렬 처리 이야기는 이런 질문 하나로 돌아온다. 이 일은 누가, 언제, 어떤 자원으로 처리해야 하는가.
