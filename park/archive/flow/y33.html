제2부 팀으로 운영하기

지워진 것을 알아차리고 되돌리는 흐름

운영하다 보면 지우려던 것이 아닌 것이 지워져 올라가는 날이 온다. 처음 하는 독자에게는 올린 직후에 무엇이 바뀌었는지를 수로 확인하게 하고, 원본이 되는 자료와 그것으로 생성한 화면을 따로 두기를 권한다. 저자의 정보 사이트에서 요리법 페이지 340개가 지워진 채 올라갔다가 5분 안에 되돌아온 일이 있는데, 되돌릴 수 있었던 것은 이 두 가지가 그렇게 되어 있었기 때문이다.

실제 흐름 · 페이지 340개가 지워져 올라갔다가 돌아오기까지 (2026년 10월 30일 14시 6분 ~ 11분)

업무: 올린 뒤에 무엇이 바뀌었는지 확인한다. 개발 세션이 안내 글과 요리법 화면의 모양을 고친 뒤 사이트 전체를 다시 생성했고, 한 시간마다 도는 예약도 같은 작업 폴더를 쓰고 있었다.
14:06 · 개발다시 생성이 끝나자 바뀐 폴더를 묶어서 올렸다. 출력에는 파일 1,796개가 바뀌었고 지워진 줄이 13,497줄이라고 나왔다
14:08 · 개발공개 주소를 열어 새 모양이 반영된 것을 확인했다
14:09 · 개발이 찾은 것올린 내용을 다시 훑다가 지워지기만 한 파일이 줄지어 있는 것을 보았다. 세어 보니 340개였고 모두 요리법 페이지였다
14:09 · 개발요리법의 원본 자료는 1,313건 그대로인 것을 확인했다. 작업 폴더에는 페이지 파일 1,353개가 그대로 남아 있었다
14:09 · 개발남아 있던 340개를 다시 넣어 올렸다
14:11 · 결과지워졌던 페이지 가운데 하나를 반복해 열어 보았다. 세 번은 열리지 않았고 네 번째에 열렸다. 그 뒤 지워진 파일이 0건인 것을 확인하고 저자에게 알렸다
페이지가 열리지 않은 시간은 짧게는 2분, 길게는 4분 30초쯤이다. 찾은 것도 되돌린 것도 올린 세션 자신이었고, 찾게 된 계기는 올린 뒤에 바뀐 파일의 수를 다시 본 것이었다.

세션은 예약으로 도는 생성과 겹쳐서 페이지를 다시 쓰는 도중의 상태가 올라간 것으로 보인다고 보고했다. 이 원인은 기록으로 확인되지 않았다. 세션은 큰 폴더를 올릴 때에는 생성이 끝난 것을 확인하고 지워지는 것이 섞이지 않았는지를 검사한 뒤 올리겠다고 적었다.

이 흐름을 다시 보면, 첫 출력에 이미 지워진 줄이 만 줄이 넘는다고 나와 있었지만 세션은 그것을 지나쳤고, 공개 주소에서 새 모양이 보이는 것만 확인했다. 확인하려던 것이 반영되었는지와, 확인하려 하지 않은 것이 바뀌지 않았는지는 따로 보아야 한다. 그리고 되돌리는 데 다시 생성할 필요가 없었던 것은 원본 자료가 건드려지지 않았고 생성된 파일도 작업 폴더에 남아 있었기 때문이며, 지워진 것은 올라간 쪽뿐이었다.

데이터의 종류와 저장 위치

이 책의 사이트에서 관리해야 하는 데이터는 크게 다섯 가지이며, 성격이 서로 달라서 저장하는 위치와 다루는 방법도 다르다.

데이터내용저장 위치주의할 점
콘텐츠글, 사진, 상품 정보프로젝트 폴더의 파일저장소에 함께 올라간다
설정사이트 이름과 색상프로젝트 폴더의 설정 파일내 컴퓨터 전용 설정은 저장소에 올리지 않는다
고객 데이터주문, 장바구니, 상품평쇼핑몰 서버의 데이터베이스 파일개인정보가 들어 있어 저장소에 올리지 않는다
작업 기록세션별 기록, 전달 폴더의 파일기록 폴더와 전달 폴더새 세션이 작업을 이어받는 근거가 된다
비밀 정보메일 비밀번호, 인증 키, 입금 계좌내 컴퓨터 전용 파일에이전트가 읽지 못하게 차단 규칙으로 막는다

여기서 중요한 구분은 저장소에 올려도 되는 것과 올리면 안 되는 것이다. 저장소를 공개로 만들면 그 안의 파일을 누구나 볼 수 있기 때문에, 고객의 연락처가 들어 있는 주문 데이터나 비밀번호가 들어 있는 설정 파일이 저장소에 포함되면 안 된다. 하네스는 이런 파일들을 저장소 제외 목록에 미리 넣어 두었고, 비밀 정보가 든 파일은 에이전트가 읽지 못하도록 차단 규칙에도 등록해 두었다. 독자가 새로운 종류의 데이터를 추가할 때도 이 구분을 먼저 확인하는 것이 좋다.

현황 확인과 백업

데이터 관리의 시작은 지금 무엇이 얼마나 있는지를 아는 것이다. 에이전트에게 데이터 현황을 물으면 글과 상품, 주문의 수와 마지막 백업 시점을 한 화면으로 정리해 보여 준다. 저자가 저장소를 새로 내려받은 직후에 확인한 현황은 다음과 같다.

┌─ 데이터 현황 ────────────────────────────────────────
│ 글 2편 · 확인 노트 5건
│ 가게: 아직 켠 적이 없습니다
│ 올린 주소: 아직
│ 마지막 백업: 없음 — python run.py 데이터 백업
└────────────────────────────────────────────────────

백업을 요청하면 콘텐츠와 설정, 고객 데이터를 하나의 압축 파일로 묶어 백업 폴더에 저장한다. 저자가 실행했을 때는 파일 38개가 4.9MB 크기의 압축 파일 하나로 저장되었고 0.4초가 걸렸다. 백업 파일은 최근 14개까지만 보관하고 오래된 것부터 자동으로 삭제한다.

백업했습니다: 백업/2026-11-12_100710.zip  (파일 38개, 4940KB) — 최근 14개만 남깁니다

이 백업은 앞에서 본 수정 전 백업과는 목적이 다르다. 수정 전 백업은 방금 한 수정을 취소하기 위한 것이어서 에이전트가 무언가를 고칠 때마다 자동으로 만들어지고, 데이터 백업은 며칠 전의 상태로 돌아가야 하는 상황에 대비해 정기적으로 만들어 두는 것이다. 또 백업 폴더는 내 컴퓨터에 있으므로 컴퓨터 자체가 고장 나는 경우까지 대비하려면 백업 파일을 외장 저장 장치나 클라우드 저장소에 따로 복사해 두어야 한다.

복구

백업은 실제로 복구가 되는 것을 확인해야 의미가 있으므로, 저자는 글이 들어 있는 폴더를 통째로 없앤 다음 복구를 요청해 보았다.

백업했습니다: 백업/2026-11-12_100710_복구직전.zip  (파일 34개, 4682KB) — 최근 14개만 남깁니다
복구했습니다: 백업/2026-11-12_100710.zip. 복구 직전 상태도 백업/ 에 남겨 두었습니다. 올려 둔 사이트에 반영하려면 python run.py 올려.

복구를 실행하자 없앴던 글 두 편이 원래대로 돌아왔다. 출력의 첫 줄에서 볼 수 있듯이 복구를 실행하면 복구하기 직전의 상태도 먼저 백업해 두기 때문에, 복구한 뒤에 오히려 잘못됐다는 것을 알게 되더라도 복구 전으로 다시 돌아갈 수 있다. 복구는 현재 데이터를 과거의 데이터로 덮어쓰는 작업이어서 에이전트가 스스로 판단해서 실행하지 않으며, 독자가 복구하라고 분명하게 요청했을 때만 실행한다. 복구한 내용은 내 컴퓨터에만 적용되므로 이미 배포한 사이트에 반영하려면 다시 배포해야 한다.

세션별 담당

데이터를 누가 관리하는지도 정해 두어야 하는데, 화면과 기능, 설정을 수정하는 것은 기본 세션이므로 백업과 복구도 기본 세션이 맡고, 매일 반복되는 현황 확인과 백업은 앞에서 소개한 데이터 서브에이전트에게 맡긴다. 데이터 서브에이전트는 현황을 확인하고 백업한 다음, 쇼핑몰에 주문이 있으면 주문 목록을 표로 내보내고, 사람이 처리해야 할 일을 맨 위에 정리해서 돌려준다. 이 서브에이전트의 정의 파일에는 하지 말아야 할 일도 적혀 있어서 복구를 실행하지 않고, 주문 목록을 외부로 옮기지 않으며, 주문 상태를 바꾸지 않는다.

작업담당주기와 조건
현황 확인과 백업데이터 서브에이전트매일 아침, 또는 기본 세션이 요청할 때
주문 목록 내보내기데이터 서브에이전트주문이 있을 때. 파일은 외부에 올리지 않는다
입금 확인과 발송 처리독자통장을 확인한 뒤 운영자 화면에서 직접 처리한다
복구기본 세션독자가 요청했을 때만
백업 파일을 다른 곳에 복사독자주 1회 정도

이렇게 나눠 두면 매일 아침 독자가 확인할 것은 데이터 서브에이전트가 정리한 한 줄뿐이어서, 입금 대기 주문이 몇 건인지와 백업이 정상적으로 만들어졌는지를 보고 필요한 처리만 하면 된다.

그래서 하네스는 이렇게 짜여 있다

흐름에서 본 것하네스에 들어 있는 것
원본 자료는 그대로였고 지워진 것은 생성된 화면이었다글과 설정이 원본이고 사이트의 화면은 명령으로 다시 생성한다. 백업은 원본을 묶는다
올린 뒤에 바뀐 파일의 수를 다시 보고 알아차렸다수정이 끝났다고 알리는 명령이 고친 파일의 목록을 보여 주고, 사이트를 생성할 때마다 글과 페이지의 수를 출력한다
되돌린 뒤에 공개 주소를 반복해 열어 확인했다올리는 명령은 주소가 열리는지를 확인한 뒤에 알리고, 복구한 뒤에는 다시 올려야 공개된 쪽에 반영된다고 출력에 적는다
같은 폴더를 세션과 예약이 함께 썼다올리는 일은 기본 세션 하나에 두었다. 예약에는 하루 작업 하나만 건다

독자가 할 일은 글의 수와 페이지의 수를 기억해 두는 것이고, 「첫 캠핑」이라면 글 여섯 편에 페이지 10개다. 요청하지 않았는데 이 수가 줄어 있으면 올리기 전에 이유를 묻는다.
